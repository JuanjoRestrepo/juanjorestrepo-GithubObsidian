# Creating a Dispatcher Project in UiPath

## Lesson Objectives
* Learn how to design and build a **Dispatcher** workflow responsible for loading transaction data into UiPath Orchestrator Queues.
* Understand the architectural advantages of decoupling the Dispatcher (Queue Producer) from the Performer (Queue Consumer).

---

## Architectural Principle: Dispatcher vs. Performer
In enterprise RPA architecture, splitting a process into **Dispatcher** and **Performer** workflows enforces single-responsibility design:
* **Dispatcher**: Reads raw data from a source (Excel, SQL, API, Web Scraping) and pushes individual transaction items into an Orchestrator Queue.
* **Performer**: Consumes items from the Orchestrator Queue (typically built on REFramework) and processes business logic for each transaction.

---

## Step-by-Step Implementation Guide

### 1. Initialize a Separate Project
* Create a standalone project in **UiPath Studio** specifically dedicated to the Dispatcher.
* Modularizing the Dispatcher separately from the Performer prevents tight coupling and simplifies lifecycle management.

### 2. Create the Dispatcher Workflow
* Add a new workflow file (e.g., `Dispatcher.xaml` or `Main.xaml`) to handle the ingestion and queue loading logic.

### 3. Implement Data Ingestion
* Add data retrieval activities based on the input source:
  * **Excel / CSV**: Use `Read Range` or `Read CSV` to store records in a `DataTable`.
  * **Databases**: Use `Execute Query` to extract records via SQL.
  * **APIs / Web**: Use `HTTP Request` or UI Automation activities.

### 4. Populate Orchestrator Queues
* Loop through the retrieved dataset using a `For Each Row in Data Table` activity.
* Insert an **Add Queue Item** activity inside the loop to push each record to Orchestrator:
  * **OrchestratorQueueName**: Specify the targeted queue name.
  * **ItemInformation**: Map dataset columns to queue dictionary key-value pairs (`ItemInformation` collection).
  * **Reference**: Assign a unique identifier (e.g., Invoice Number, ID) to enable item deduplication and tracking.

### 5. Publish to Orchestrator
* Save and validate the workflow.
* Click **Publish** on the top ribbon to deploy the Dispatcher package to **UiPath Orchestrator**.

### 6. Configure Triggers in Orchestrator
* Navigate to **Triggers** in Orchestrator.
* Set up a **Time Trigger** (or Scheduled Run) to execute the Dispatcher periodically (e.g., daily at 06:00 AM) to refresh queue stock.

### 7. Link to Performer Execution
* Configure the Performer process to be triggered either via a **Queue Trigger** (executes automatically as soon as queue items are added) or a scheduled time window following Dispatcher completion.

---

## Key Benefits of a Dispatcher Architecture
* **Scalability**: Enables parallel processing by firing multiple Performer bots to consume items simultaneously from a single queue.
* **Maintainability**: Allows changes to data extraction logic without modifying core business processing rules in the Performer.
* **Fault Isolation**: Source file/system failures during ingestion do not affect already queued transactions.

---

## Conclusion
Decoupling data loading into a dedicated Dispatcher project ensures clean architecture, enables queue-driven parallel processing, and increases overall automation resilience.
