### Tenemos una Región de Infraestructura de Oracle Cloud (OCIR)

1. Esta región está formada pro varios Dominios de Disponibilidad (**Availability Domain**). Estos son nada más que **Data Centers**
2. La Primera Dependencia que tiene el Servicio o Hosts Informáticos es la ***Red Virtual en la Nube***
	1. Esta Network se divide en Subnets/Subredes
	2. Las Subnets se deben crear antes de crear un Host de Recursos Informáticos

![[Pasted image 20260622144637.png]]


3. Un **Host Informático (Compute Host)** es una ***construcción física***
4. Las **Redes (Networking)** son una ***construcción virtual***
	- Cómo se relacionan?
		- Dentro del Compute Host existe una **Tarjeta de Interfaz de Red Física (Networking Interface Card)** Esta se virtualiza
		- Al virtualizarla obtenemos una **VNIC (Virtual Network Interface Card)**
		- Esa VNIC se coloca dentro de una Subnet

	![[Pasted image 20260622145815.png]]
	

	- De ahí es donde proviene la **IP Private** del host de recursos informáticos (Compute Host)
	- Cada Compute Host o VM que se ejecute (running) tiene una IP Privada

5. El ***Boot Volume*** o ***Disco de Inicio*** es otra dependencia de las Compute Instances
	- Cada uno de estos Compute Hosts activados tienen un OS
	- La imagen de ese OS para hacer booting de una instancia determina el tipo de OS y algún otro software que requiera 

	![[Pasted image 20260622150221.png]]


6. También tiene **Datos/Data** como **File Systems (Sistemas de Archivos**) los cuales también viven en la Red/Network

## Direct Migration / Migración en vivo

Sabemos que los computadores pueden fallar. Entonces 

***¿Cómo nos aseguramos que cualqwuier Host Informático que esté corriendo, siempre esté activo y en ejecucicón?***

![[Pasted image 20260622151611.png]]

 ### Aquí entra la función ***Live Migrate***

### Live Migare
- Si alguno de esos hosts se cae o presenta problemas, migraríamos la VM a otro host nuevo de nuestro Data Center
- Esto se transparente
- No requiere rebooting/reiniciar
- Las aplicaciones se ejecutan incluso durante eventos de mantemiento (NO DOWNTIME)
- No es trivial la tarea/Seamless


## Scaling

Existen dos tipos:
1. Vertical
2. Horizontal

### Vertical Scaling

![[Pasted image 20260622152243.png]]

1. Se amplian o reducen las unidades de instancia
2. La nueva shape debe tener la misma arquitectura del hardware
3. Una buena práctica es parar la instancia antes de ampliarla verticalmente

#### ¿Qué se puede escalar?
- El curso
- La memoria

> Cuando se escala, se requiere de un ***tiempo de inactividad (Downtime)***


### Horizontal Scaling (Autoscaling)

![[Pasted image 20260622153123.png]]

1. Agregar más VMs de la misma unidad o que tome un poco más de la misma unidad ya existente
2. Esto permite despliegue a gran escala en VMs
3. **Scale-out** or **Scale-in** (El primero de la imagen, donde va de una VM a 4 VMs y el segundo de abajo, donde pasamos de 4 VMs a una sola VM )

### ¿Por qué es poderoso y popular?

1. Da la capacidad de ampliacion y de alta disponibilidad
2. Si una VM falla, las otras pueden seguir trabajando
3. Puede hacer coincidir la demanda de tráfico agregando o eliminando VMs automáticamente
4. No hay costo adicional para Autoscaling
