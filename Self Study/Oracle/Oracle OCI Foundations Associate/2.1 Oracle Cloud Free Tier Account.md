2. La Primera Dependencia que tiene el Servicio o Hosts Informáticos es la ***Red Virtual en la Nube***
	1. Esta Network se divide en Subnets/Subredes
	2. Las Subnets se deben crear antes de crear un Host de Recursos Informáticos

![[Pasted image 20260622144637.png]]


3. Un **Host Informático (Compute Host)** es una ***construcción física***
4. Las **Redes (Networking)** son una ***construcción virtual***
	- Cómo se relacionan?
		- Dentro del Compute Host existe una **Tarjeta de Interfaz de Red Física (Networking Interface Card)** Esta se virtualiza
		- Al virtualizarla obtenemos una **VNIC (Virtual Network Interface Card)**
		- Esa VNIC se coloca dentro de una Subnet

	- De ahí es donde proviene la **IP Private** del host de recursos informáticos (Compute Host)
	- Cada Compute Host o VM que se ejecute (running) tiene una IP Privada

5. El ***Boot Volume*** o ***Disco de Inicio*** es otra dependencia de las Compute Instances
	- Cada uno de estos Compute Hosts activados tienen un OS
	- La imagen de ese OS para hacer booting de una instancia determina el tipo de OS y algún otro software que requiera

6. También tiene **Datos/Data** como **File Systems (Sistemas de Archivos**) los cuales también viven en la Red/Network

## 1.2 Scaling

Existen dos tipos:
1. Vertical
2. Horizontal

### Vertical Scaling

![[Pasted image 20260622152243.png]]

1. Se amplian o reducen las unidades de instancia
2. La nueva shape debe tener la misma arquitectura del hardware
3. Una buena práctica es parar la instancia antes de ampliarla verticalmente

#### ¿Qué se puede escalar?
- El curso
- La memoria

> Cuando se escala, se requiere de un ***tiempo de inactividad (Downtime)***


### Horizontal Scaling (Autoscaling)

![[Pasted image 20260622153123.png]]

1. Agregar más VMs de la misma unidad o que tome un poco más de la misma unidad ya existente
2. Esto permite despliegue a gran escala en VMs
3. **Scale-out** or **Scale-in** (El primero de la imagen, donde va de una VM a 4 VMs y el segundo de abajo, donde pasamos de 4 VMs a una sola VM )

### ¿Por qué es poderoso y popular?

1. Da la capacidad de ampliacion y de alta disponibilidad
2. Si una VM falla, las otras pueden seguir trabajando
3. Puede hacer coincidir la demanda de tráfico agregando o eliminando VMs automáticamente
4. No hay costo adicional para Autoscaling


### Cómo hacerlo en la práctica?
#### 1. Definición de la Configuración (Instance Configuration)
El primer paso es capturar el "estado deseado" de tu instancia. Esta configuración actúa como un **blueprint** (plantilla) que el sistema utilizará para aprovisionar nuevas instancias automáticamente.

- **Contenido:** Imagen del SO, _shape_ (CPU/RAM), metadatos, configuraciones de red (VNIC, subnets), y almacenamiento (boot volume/block volumes).
- **Propósito:** Garantizar que cada nueva instancia sea idéntica a la original.

![[Pasted image 20260622160927.png]]


#### 2. Creación del Grupo de Instancias (Instance Pool)
Una vez definida la configuración, creas un **Instance Pool**. Este es un contenedor lógico que agrupa instancias creadas a partir de la configuración anterior.

- **Gestión Unificada:** Permite realizar operaciones masivas (Start, Stop, Terminate) sobre el grupo como si fuera una sola unidad.
- **Alta Disponibilidad:** Puedes distribuir las instancias a través de múltiples **Availability Domains (ADs)** o Fault Domains para asegurar tolerancia a fallos ante una caída de un centro de datos.


![[Pasted image 20260622160941.png]]


#### 3. Configuración de Reglas de Autoscaling
Finalmente, aplicas las políticas de escalado sobre el _Instance Pool_. Aquí es donde defines los límites y la lógica operativa.

- **Parámetros críticos:**
    - **Initial Size:** Número de instancias al arrancar.
    - **Min/Max Size:** Límites superior e inferior para evitar costos excesivos o caídas por falta de capacidad.
        
- **Lógica de Escalado:** Se basa en métricas de rendimiento (CPU o memoria).
    - _Scale-out:_ Se añaden instancias si el uso supera un umbral definido (ej. > 70%).
    - _Scale-in:_ Se eliminan instancias si el uso cae por debajo de un umbral definido, optimizando costos.

## 1.3 OCI Cloud Shell: Configuración y Uso Práctico

Cloud Shell es un terminal basado en navegador que proporciona una máquina efímera preconfigurada con el CLI de OCI y herramientas de desarrollo, eliminando la necesidad de configuraciones locales y evitando problemas de interoperabilidad entre sistemas operativos (Windows/macOS/Linux).

### 1. Configuración de Permisos (IAM Policy)
Antes de acceder, el usuario debe tener permisos explícitos en el _tenancy_. La política debe permitir el uso de Cloud Shell para el grupo correspondiente:

```Bash
Allow group <Nombre_Grupo_Admin> to use cloud-shell in tenancy
```

### 2. Acceso y Entorno

- **Instanciación:** Al hacer clic en "Cloud Shell" en la consola, OCI aprovisiona automáticamente una máquina Linux temporal en el backend.
- **Pre-configuración:** Incluye la versión más reciente del OCI CLI y utilidades estándar (git, kubectl, terraform, etc.).

### 3. Caso de Uso: Generación de Pares de Llaves SSH

Cloud Shell facilita la gestión de llaves sin exponer el almacenamiento local de tu máquina física.

**Pasos:**

1. **Directorio de trabajo:** Crear un directorio dedicado para organizar las llaves.
```Bash
mkdir ~/.ssh
cd ~/.ssh
```

2. **Generación de llaves:** Utilizar `ssh-keygen` para crear el par de llaves (pública y privada).

```Bash
ssh-keygen -t rsa -b 2048 -f <nombre_de_llave>
```

- `-t rsa`: Algoritmo de cifrado.
- `-b 2048`: Longitud mínima recomendada para OCI (bits).
- `-f`: Nombre del archivo resultante.

3. **Resultado:**
	- `nombre_de_llave`: Llave privada (se mantiene segura en el _home_ de Cloud Shell).
	- `nombre_de_llave.pub`: Llave pública (se utiliza al configurar nuevas instancias de cómputo para permitir el acceso vía SSH).

> **Nota de Seguridad:** La llave privada permanece en el almacenamiento efímero de tu sesión de Cloud Shell. Al ser una herramienta basada en la nube, el entorno está aislado, lo que reduce riesgos de exposición de credenciales en tu máquina local.

## 1.4 Creación de Instancia de Cómputo (Compute Service)

El despliegue de una instancia es el proceso fundamental de aprovisionamiento en OCI. Este proceso se gestiona desde el **Compute Service** y requiere definir parámetros de hardware, red y seguridad.


### 1. Parámetros Principales de Configuración
Para instanciar una máquina virtual, se deben configurar los siguientes componentes:
- **Compartment:** Define el alcance lógico y el aislamiento de recursos (ej. _sandbox_).
- **Availability Domain (AD) / Fault Domain (FD):**
    
    - **AD:** Centro de datos físico aislado.
    - **FD:** División lógica dentro de un AD para redundancia (cada AD tiene 3 FDs).
        
- **Imagen (OS):** Selecciona el sistema operativo (ej. Oracle Linux, Windows). Permite imágenes personalizadas o de terceros.
    
- **Shape:** Define la capacidad de cómputo (CPU, RAM, red). Permite elegir arquitectura del procesador (**AMD, Intel, ARM**).
    - _Nota:_ Existen tipos _Always Free_ para despliegues sin costo.

### 2. Infraestructura de Red (VCN y Subnets)
Si no existe una infraestructura previa, el asistente de OCI aprovisiona automáticamente:

- **VCN (Virtual Cloud Network):** Red privada virtual.
- **Subnet:** Necesaria para la conectividad de la instancia.
- **Direccionamiento IP:**
    - **Public IPv4:** Asignada si se requiere acceso desde internet.
    - **Private IPv4:** Configuración estándar para servicios internos (ej. bases de datos).
    
### 3. Seguridad y Acceso
El método recomendado de acceso es mediante el par de **llaves SSH** generado previamente en Cloud Shell:

1. **Public Key:** Se pega en la consola de OCI durante la creación de la instancia.
2. **Private Key:** Se utiliza desde el cliente (Cloud Shell) para autenticarse contra la instancia.
