Es común que los proyectos de automatización encuentren eventos que interrumpen o interfieren con la ejecución proyectada. Algunos de estos se identifican en las fases de desarrollo y prueba, y se implementan mecanismos de manejo.

Considere una automatización donde los datos de entrada provienen de un formulario web y la aplicación intenta hacer coincidir los datos con la lista de clientes existentes usando el apellido. Pero, ¿y si el usuario se equivoca al escribir el nombre? Naturalmente, el nombre no será reconocido.

Un buen diseño de proyecto incluirá formas de reconocer e identificar la excepción, y también patrones de acción que se ejecutan solo cuando se detectan excepciones. Estos pueden será simplemente detener la ejecución, o acciones explícitas ejecutadas automáticamente dentro del flujo de trabajo, o incluso escalar el problema a un operador humano.

La predicción y el tratamiento de las excepciones se pueden hacer de dos maneras:

- At activity level, using **Try/Catch** blocks or **Retry Scope**.
    
- At a global level, using the **Global Exception Handler**.


Ambos se tratarán en profundidad en el curso Manejo de errores y excepciones en Studio. En este punto, es importante poder elegir el tipo correcto de excepción, ya que la información se utilizará en un nivel superior más adelante en el desarrollo para tomar otras decisiones. Las categorías de excepciones son:


## Excepción de aplicación

La Excepción de la aplicación describe un error originado en un problema técnico, como una aplicación que no responde.

Considere un proyecto que extraiga números de teléfono de una base de datos de empleados e insértelos en una aplicación financiera. Si al intentar la transacción la aplicación financiera se congela, el Robot no puede encontrar el campo donde debe insertar el número de teléfono y eventualmente arroja un error. Este tipo de problemas tienen la posibilidad de resolverse simplemente volviendo a intentar la transacción, ya que la aplicación puede descongelarse.

Al administrar excepciones de aplicaciones, es extremadamente importante tener buenas convenciones de nomenclatura para actividades y flujos de trabajo. Esto ayudará con el seguimiento de la actividad que causó la excepción.

## Excepción de regla de negocio

La excepción comercial describe un error que se origina en el hecho de que ciertos datos de los que depende el proyecto de automatización están incompletos, faltan, están fuera de los límites establecidos (como tratar de extraer del cajero automático más que el límite diario) o no pasan otros criterios de validación de datos (como el monto de una factura que contiene letras). Las excepciones a las reglas de negocio no ocurren "naturalmente", deben definirse mediante una actividad de lanzamiento.

Considere un robot que procesa facturas, con una regla comercial establecida por el propietario del proceso de que solo las facturas con un monto inferior a $ 1000 deben ingresar al proceso automatizado. Para los demás, se aplica un flujo diferente, que involucra a un usuario humano para procesarlos.

En este caso, volver a intentar la transacción no ofrece ninguna posibilidad de resolver el problema, sino que se debe notificar al usuario comercial sobre la factura pendiente y el caso debe tratarse como una excepción comercial, porque es una excepción del flujo de proceso habitual y la validación la realiza explícitamente el desarrollador dentro del flujo de trabajo.

Como práctica recomendada, el texto de la excepción debe contener suficiente información para que un usuario humano (usuario comercial o desarrollador) comprenda qué sucedió y qué acciones deben tomarse.
