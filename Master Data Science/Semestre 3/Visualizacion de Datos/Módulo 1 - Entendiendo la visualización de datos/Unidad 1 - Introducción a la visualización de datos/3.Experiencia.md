## Accesibilidad en visualizaciones y dashboards

**Cada usuario es único**. 
Para atender a un público diverso y a personas con discapacidad (quienes representan alrededor del 15-20% de la población mundial) **es vital diseñar dashboards y visualizaciones accesibles.** Más aún, *la accesibilidad suele mejorar la experiencia de todos los usuarios* infogram.coma11y-collective.com

Productos digitales accesibles e inclusivos no solo cumplen con marcos como las WCAG 2.1, sino que amplían el mercado y mejoran la satisfacción general. 

En el caso de **dashboards analíticos**, esto implica `considerar aspectos visuales (colores, textos, gráficos), interacción (navegación por teclado, foco) y contenido alternativo (texto, tablas)` para que **la información llegue por completo** a usuarios con limitaciones visuales, motoras, cognitivas o de otro tipo.

### 1. Contraste de color y uso del color

**1.1.** Un contraste alto entre texto o elementos gráficos y su fondo es fundamental para la legibilidad. 
Los lineamientos WCAG recomiendan una relación de contraste de al menos `4.5:1 `para texto normal, o `3:1` para texto grande o negrita. 

Por ejemplo, si se usa texto blanco sobre fondo oscuro u otros pares extremos (negro/amarillo vs blanco), la lectura es mucho más cómoda que combinaciones de bajo contraste (gris claro sobre gris medio). El párrafo siguiente ilustra esto:

**1.2.** El contraste deficiente complica la lectura, especialmente para personas con baja visión.

En la práctica, conviene usar herramientas de comprobación de contraste (p.ej. `WebAIM` o extensiones como `Stark`) para verificar combinaciones de colores. 

Además, no debe usarse el color como única vía de comunicación. **Siempre agregue señales visuales** adicionales cuando el color diferencia categorías (por ejemplo,` texturas, patrones, íconos`). 

Un gráfico de barras con cada serie en distintos patrones ayuda a personas con daltonismo a distinguir las categorías, como se muestra a continuación

**1.3.** Finalmente, **evite modas estéticas de texto de muy bajo contraste (gris sobre gris)**. Estudios de Nielsen Norman demuestran que e**l texto poco contrastado reduce la legibilidad y la confianza del usuario**, *dificulta encontrar elementos y provoca fatiga visual.* 

En especial en móviles o entornos con luz, estos textos casi no se leen. Si se busca reducir la prominencia de una sección, use otras estrategias (*mayor espacio en blanco, tipografía menor o despliegues colapsables*) en lugar de bajar el contraste

### 2.Tipos de letra y tamaño legible

**2.1.** Elija fuentes legibles (tipografía clara, preferentemente sans serif) y evite tamaños muy pequeños. 
El texto debe poder ampliarse al menos un 200% sin romper el diseño (WCAG 2.1 SC 1.4.4). 
Un buen punto de partida es usar `8pt` o más para **texto de cuerpo** y **mayor para títulos**. Para destacar información, aumentar el tamaño de letra de subtítulos o porcentajes suele ser más efectivo y accesible que atenuarlos por color.

### 3. Indicador de foco y navegación por teclado

**3.1.** **Los dashboards interactivos deben ser navegables sin mouse.** 

Toda interacción (`botones, filtros, menús, enlaces`) debe **recibir foco de teclado y mostrar un indicador visual claro cuando esté seleccionado.** 

Por ejemplo, *browsers dibujan por defecto un contorno azul alrededor del elemento con foco*; use ese mismo contorno (o uno personalizado, visible y con alto contraste) **para que el usuario sepa dónde está la navegación en cada momento.** 

Nunca elimine el outline de foco mediante CSS, pues esto deja sin señal a los usuarios que tabulan con teclado. 

En resumen, **asegúrese de que el indicador de foco sea fácilmente perceptible** (por ejemplo, `borde grueso o cambio de color fuerte`) cuando el usuario navegue con Tab.

### 4. Texto alternativo y descripciones

**4.1.** Según WCAG (SC 1.1.1), **todo contenido visual no textual debe tener una alternativa textual**. Para un dashboard esto incluye `gráficos, imágenes y diagramas. `

Debe agregarse **alt text** *a las imágenes de gráficos simples que explique brevemente el mensaje principal.* 

Para gráficos más complejos, lo ideal es **ofrecer un resumen textual cercano y una tabla de datos legible.** Por ejemplo: “*Gráfico de barras que muestra ventas por mes: marzo 30%, abril 25%, entre otros*” **junto con una tabla de esos valores.**

Si no cabe una descripción extensa en el contexto, use `aria-describedby` **para referir a un texto explicativo largo en otra parte.** 

En todos los casos, `provea leyendas, títulos, etiquetas de ejes, valores de datos y descripciones de los puntos clave`. Un buen alt text debe mencionar las principales conclusiones o tendencias, sin ser tan corto que omita la esencia.



### 5. Paleta de color y elementos visuales
**5.1.** Elija paletas con suficiente contraste y amigables para daltónicos. 
Algunas combinaciones (`rojo-verde, azul-púrpura o verde-amarillo`) son problemáticas para varios tipos de daltonismo. 

Para gráficos con varios colores, existen generadores accesibles (`ColorBrewer, Venngage, accessible-colors, etc.`) que sugieren combinaciones seguras. 

También conviene simular visiones daltónicas con extensiones o herramientas de desarrollo para comprobar que el gráfico permanezca inteligible. 

En resumen, **use contrastes altos para texto y datos**, y **apoye la distinción de categorías con texturas o formas adicionales en vez de depender sólo del color.**


### 6. Interacción y accesibilidad en gráficos

**6.1. Elementos interactivos accesibles**
Todo control dentro de un gráfico (botones de filtro, selectores de rango, etc.) debe ser operable con teclado y tener labels claros (p.ej. aria-label o texto visible)

**6.2. Herramientas emergentes (tooltips)**
Si los puntos de datos muestran información adicional al pasar el mouse, asegúrese de que esas descripciones también sean accesibles con teclado y legibles por lectores de pantalla

**6.3. Tablas de datos**
 Siempre ofrezca la posibilidad de ver los datos sin gráfico, ya sea mediante una tabla debajo del gráfico o un enlace de descarga (CSV, Excel). Esto es útil para usuarios que prefieren o necesitan procesar los datos textualmente.
 
**6.4. Selección de visualizaciones**
Para datos simples, favorezca gráficos estáticos sencillos (barras, líneas, tartas con pocos segmentos) sobre visualizaciones complejas o muy interactivas. Los gráficos estáticos son más fáciles de interpretar y compatible con tecnologías asistivas.

Si debe usar gráficos múltiples, etiquete cada eje y serie claramente, y distinga líneas con marcadores o estilos diferentes (rayas, puntos, etc.) para ayudar a quienes tienen baja visión.

**6.5. Revisar con usuarios reales**
Finalmente, pruebe los dashboards con personas que usen lectores de pantalla, lupas o que tengan diferentes discapacidades. La prueba con usuarios reales revela problemas que ni las métricas ni las comprobaciones automáticas detectan.
